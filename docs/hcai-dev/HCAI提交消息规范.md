# HCAI 提交消息规范

适用于 HCAI 人工创建的功能、修复、合并、文档、测试、版本与工程提交，以及 HCAI PR 标题和 squash 最终消息。

## 1. 统一格式

```text
hcai(<type>): <摘要>

原因：为什么修改
改动：修改什么、影响什么
验证：命令与结果，未执行则说明
风险：迁移、配置、兼容与回退影响
```

固定小写 hcai 前缀。冒号后一个空格；摘要可中文或英文，简洁描述结果，不写空泛的 update/fix bug。正文简单改动可省略，涉及计费、迁移、安全、多节点及上游合并时必须有。

正确：hcai(fix): 修复插件管理开关持久化。
不采用：fix(hcai): ...、hcai-fix: ...、feat(hcai): ...、fix: ...。历史记录存在旧形式，不要求批量改写。

## 2. 类型

| type | 使用范围 | 示例 |
| --- | --- | --- |
| feat | 新功能 | hcai(feat): 添加审核节点状态视图 |
| fix | 行为缺陷 | hcai(fix): 限定渠道价格优先级仅影响模型广场 |
| refactor | 保持外部行为的结构调整 | hcai(refactor): 整理上游倍率探测状态更新 |
| perf | 性能改进 | hcai(perf): 减少账户列表重复查询 |
| docs | 文档 | hcai(docs): 补充多区域部署规范 |
| test | 测试 | hcai(test): 覆盖跨区域 API Key 失效 |
| ci | 检查和发布自动化 | hcai(ci): 修复内嵌前端构建顺序 |
| build | 构建及依赖 | hcai(build): 对齐 pnpm 锁文件版本 |
| chore | 非业务维护 | hcai(chore): 清理废弃开发配置 |
| merge | 上游合并 | hcai(merge): 同步上游 v0.2.7 并保留 HCAI 定制 |
| release | 版本与发布准备 | hcai(release): 准备 0.2.7-hcai.1 |
| revert | 撤销已共享改动 | hcai(revert): 撤回模型广场价格展示改动 |

不破坏现有格式的情况下，在正文写 BREAKING CHANGE: 描述不兼容行为、迁移和运维要求，不只写“重大更新”。

## 3. 提交边界

一个提交一个清晰目的。业务实现、直接回归测试、相关 locale 和必需生成文件可以一起提交；无关格式化、依赖升级或版本改动应拆开。版本发布提交必须能对应发布单。

提交前检查 git diff --cached --stat 和完整暂存 diff；不能盲目 git add . 混入前一项任务或他人改动。禁止凭据、数据库备份、生产日志和未脱敏截图。新文档即使被忽略也只显式添加目标文件。

## 4. PR 和合并消息

HCAI PR 标题使用同一格式；dev → main 示例：
hcai(release): 发布 0.2.7-hcai.1。

Squash 合并时确认最终消息仍符合规范；普通 PR merge 提交建议在允许编辑时使用 hcai(merge): ...。上游原始提交与历史 GitHub 自动生成的 Merge pull request 消息保持原样，不为统一风格重写来源历史。机器人消息可以明确标识自身，不能强行伪造人工提交。

## 5. 写错后的处理

尚未推送且确定是本人最新提交，可在确认工作区/暂存内容后 amend，只改消息时不要混入其他变更。已推送到私人贡献分支，需要协作者同意才可改写，推送使用带预期基线保护的 force-with-lease。

dev/main 已共享的历史不 amend、不强推；确需撤销功能用新的 revert 提交。修改 PR 标题不能改变既有 commit message。用户要求“撤回远程”必须先确认具体提交、依赖、分支与是否已发布，优先可追溯 revert，不执行宽泛历史回滚。
