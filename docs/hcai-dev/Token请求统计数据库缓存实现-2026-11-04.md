# Token 请求统计数据库缓存实现

日期：2026-11-04；基于本地 `382bc8626` 及前一阶段未提交优化。状态：本地实现，未部署。用户确认各应用共用 PostgreSQL、Redis 不保证共享，生产只读核验暂时跳过。

## 实现

本记录取代[首轮记录](Token请求统计高IO排查与优化-2026-11-04.md)中 Redis 方案的当前实施结论，保留首轮历史证据。前端防重、取消、60 秒缺省刷新、分钟截止时间、单次聚合和原指标表达式不变。

- 迁移 `249_ops_token_stats_cache.sql` 新建 `ops_token_stats_cache`：`cache_key TEXT PRIMARY KEY`、`payload JSONB NOT NULL`、`expires_at TIMESTAMPTZ NOT NULL`。仅缓存聚合响应，不含原始请求内容。到期列索引用于小表过期清理，不给 usage_logs 新增索引。
- 远程 main 迁移已到 248，故使用 249；不修改已发布迁移，不要求回填，不扫描/改写 usage_logs。`CREATE TABLE/INDEX IF NOT EXISTS` 可重放。
- service 保留同进程 singleflight，缓存与锁由 repository 使用同一 PostgreSQL 完成；移除本接口 Redis 客户端字段和 provider/Wire 注入，不依赖 Redis 拓扑。
- key 覆盖全局管理员权限范围版本、UTC 起止时间、平台、分组、时间范围、Top N、页码和每页条数；当前 timezone 不影响此滚动窗口计算。将来若增加行级管理员权限或时区口径，须同步改 key/scope。
- 先按主键读取未到期缓存，查询最长 2 秒。命中直接返回，不读取 usage_logs；TTL 120 秒，分钟时间桶与真实 end_time 保留，成功响应正常新鲜度仍约不超过 118 秒加传输时间。新分钟会使用新 key，TTL 不是将窗口固定 120 秒。
- 未命中进入 READ COMMITTED 事务，设置事务局部 `statement_timeout=55s`、`idle_in_transaction_session_timeout=60s`、`lock_timeout=1s`。事务级 `pg_try_advisory_xact_lock(1330664276,1)` 是整个端点的全局计算门，不同条件也只能有一个明细计算。
- 锁是 PostgreSQL 事务资源，不依赖租约、Redis、应用进程或单一节点；提交、回滚、连接断开时释放。服务端 statement/idle 超时约束断线未立即检测的情况；无会话级锁，不会把锁留在连接池。兼容事务级连接池模式，不能在只读副本上提供缓存计算服务。
- 锁后再次读取缓存，消除“另一实例刚提交”的竞态；READ COMMITTED 的新 statement snapshot 能看到刚提交结果。仍未命中才运行一次物化聚合。
- 聚合结果 UPSERT 和过期清理与计算同事务提交。到期使用数据库时钟；清理每次最多删除 1000 条过期行，有到期索引且受全局计算锁串行化。没有额外后台任务，也不依赖跨节点定时任务领导者。
- 抢锁失败立即回滚释放连接，再每 250ms 检查结果并重试；两次检查之间不占连接或事务。同条件等待者可直接读取首个实例的结果；整个请求最多 58 秒，超时返回可重试 `OPS_STATS_BUSY`，不无限排队。不同时抢到锁的事务不会阻塞在 advisory lock 上。
- 缓存表不可用、数据库错误或反序列化失败时不绕过缓存直查明细；查询/写缓存/清理/提交失败不发布半成品，事务回滚释放锁。成功缓存可在后续请求中复用，错误不缓存。
- 首个进程内同 key 请求的取消会取消该次计算，等待者可以重试；独立等待者取消不影响已有首请求。context 传到 QueryRowContext，数据库执行被取消。

## 成本和边界

热请求增加一次小表主键读取，冷请求增加短事务、锁检查、缓存写入和最多 1000 行过期清理。只有冷计算持有长事务/连接（最长约 58 秒），期间会占一个连接并可能影响表 DDL/清理窗口；等待者短暂借用连接轮询。不同条件排队可能达到超时；该取舍优先保护共享数据库 IO。等待流量经各实例 singleflight 合并，同实例同 key 仅一个轮询者。

所有应用必须连接同一可写 PostgreSQL 逻辑数据库并更新为新实现。混跑旧版时，旧版仍可能直接扫描/使用独立 Redis，此锁不能限制不遵守同一锁协议的旧代码。数据库多主、只读副本路由、不同数据库、SQL 代理不保持事务语义均不在保证范围。迁移表不可用时接口报错，不退回旧重查询。

TTL 逻辑过期不等于立即物理删除；后续冷计算会分批清理。正常每分钟条件数为小表容量主因；高基数恶意管理员流量仍需现有管理员限流。若需主动清理只能按运维流程删除过期缓存，不应重置全库。

## 验证

在本机隔离 PostgreSQL 17 使用两个独立 `sql.DB` 连接池、独立 schema，应用迁移两次检验幂等。每次明细扫描由测试 view/sequence 计数（非生产结构），验证：

1. 两连接池并发同条件只扫描一次，两个结果都成功；删掉统计源后另一个实例仍命中共享缓存。
2. 过期结果不会返回；计算失败后锁释放，缓存不被刷新成错误值。
3. 平台、分组、Top N、页码/页大小、时间边界的 key 隔离。
4. 全局锁已持有时不同条件不扫描；等待取消后不占事务。
5. 扫描中取消释放数据库锁，不产生成功缓存。
6. 每次只清理 1000 条到期结果；1200 条到期测试数据留下 200 条。
7. 缓存表缺失时失败关闭，无明细扫描。
8. 原统计语义/NULL/零值/空页、service key 和 singleflight/取消测试保持通过。

定向 `-race` 加真实 PostgreSQL 集成测试通过。合成单行源每次人为延迟 200ms 的验证中，两连接池冷请求共同完成约 254.7ms，跨池热命中约 0.27ms；这些数值仅证明缓存路径，不是生产耗时预测。标准和 embed 后端构建通过，`git diff --check` 通过。运行：在隔离库设置 `OPS_TOKEN_STATS_TEST_DSN`，执行 `go test -race ./internal/repository ./internal/service -run 'TestTokenStats|TestOpsServiceGetOpenAITokenStats|TestOpsRepositoryGetOpenAITokenStats' -count=1`。

后端全量 `go test -tags=unit ./...` 与 `go test ./...` 仍由入场已有 `TestOpenAIReasoningEffortPolicyForCompositeTarget` 失败阻塞，未修改其业务文件。生产版本/计划/IO 改善按用户要求不核验，不把本地结果当生产验收。前端未在本次追加阶段修改，沿用首轮已完成的全量前端验证记录。
