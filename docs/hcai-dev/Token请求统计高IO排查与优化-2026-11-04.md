## 2. 现场与根因证据分级

### 用户已确认的现场（本次未独立采样）

日本数据库 2 vCPU、约 4 GB 内存；usage_logs 约 595 万条，heap 约 5.4 GB、含索引约 15 GB；读取约 128 MiB/s，IO wait 61%～89%，计算 CPU 不高。两应用的运维页访问 `openai-token-stats?time_range=30d&top_n=20&timezone=Asia/Shanghai`，单次 40～44 秒，默认刷新 30 秒。

这些信息与读取瓶颈相符，但尚不能证明磁盘供应商限速、具体 SQL 计划、缓存命中率、索引缺失、表膨胀或 CPU 容量不足。

### 代码与受控实测已确认

1. **一个 HTTP 请求执行两条明细查询**：相同 CTE 先取模型分组总数，再取聚合指标和 Top N/分页。PostgreSQL 可裁剪计数查询里未使用的均值，但仍读取符合条件的明细并按模型分组，不应简单称为“所有计算重复两遍”。
2. **Top N 不限制明细扫描**：LIMIT 位于 GROUP BY 和排序之后。
3. **统计覆盖所有平台**：接口名称保留 OpenAI，但缺省 platform 为空，无模型前缀限制。只有传 platform 才关联 groups/accounts，用 `COALESCE(NULLIF(g.platform,''), a.platform)` 过滤；group_id 直接过滤 usage_logs.group_id。
4. **时间为滚动时长**：默认 30d，支持 30m/1h/1d/15d/30d，SQL 是 `[start,end)`。此接口不解析 timezone，也不按本地自然日分桶；`Asia/Shanghai` 原来不影响结果。本次保持这一语义，没有把时区换成新的统计口径。
5. **卡片请求可以重叠**：父组件定时刷新核心面板成功后递增 refreshToken，但核心 loading 不覆盖 Token 请求耗时；原卡片无 signal、请求序号或 in-flight 防重，老响应可能覆盖新筛选。原分页越界代码更新 page 后直接请求，同时触发 watcher，再次请求。
6. **隐藏页/多页面/多实例放大**：原定时器无 visibility 判断；不同页面彼此独立；原后端无缓存、singleflight 或共享互斥。浏览器定时器节流不能当成暂停保证。
7. **初始挂载**：卡片由 `showOpenAITokenStats && !(loading && !hasLoadedOnce)` 控制，首次核心加载结束后挂载，立即加载；正常首次挂载并无固定双发证据。开关关闭后会卸载，重新开启会重新加载。筛选改变可能先触发卡片，再由父刷新信号触发，原实现无统一防重。
8. **HTTP 超时不匹配**：通用 apiClient 超时 30 秒，短于用户观测的查询耗时；本次只将此端点改为 65 秒。

### 未取得的生产证据

当前二进制/前端 SHA、实际持久化刷新设置、两实例是否共享同一 Redis 实例与 DB、数据库版本与执行计划、近月行数/大小增长、analyze/vacuum 时间、死元组、事故窗口缓存命中率、磁盘规格/吞吐额度、pg_stat_statements 数据均未现场核实。生产耗时/读取/并发改善不能标为已验证。

提供了[生产只读检查 SQL](Token请求统计生产只读检查-2026-11-04.sql)。优先执行普通 EXPLAIN；严禁直接在繁忙生产库对 30d 做 EXPLAIN ANALYZE。统计计数需要两次采样差值，不能把生命周期命中率当现场命中率，不能把 n_dead_tup 估计当表膨胀定论。

## 3. 本次实现

### 前端

- 运维仪表盘缺省刷新间隔 30 → 60 秒。影响父页面共享节奏（核心面板、并发卡、Token 卡、系统日志等接收刷新信号的组件）；并非修改全站所有独立定时器。
- 后端高级设置默认/缺省回填也改为 60；**数据库已有 30 等显式值保持不变**。上线需通过现有运维设置界面核对/改为 60，代码不会擅自写生产设置。
- Token 卡同条件在途时跳过 refreshToken；筛选、Top N、页码变化则取消旧请求并立即发起新请求，序号和 signal 双重保护，不让旧响应覆盖新值。
- 越界分页只修改 page，由 watcher 唯一重查。
- 页面隐藏暂停父定时器、取消当前 Token 请求；恢复重置完整倒计时，不立即补发。自动刷新关闭时恢复不会自动查询，可手动刷新；隐藏期间改筛选也待下一次正常刷新/手动刷新生效。
- 卸载移除 visibility listener、取消请求，父页面清理定时器。
- 保留原有统计范围选择和 30d 初始值；新增卡片手动刷新、显示数据截至时间；保留加载/错误显示。父定时失败也先重置倒计时，避免每秒重试。

### 单次明细扫描

`WITH stats AS MATERIALIZED (...)` 只执行一次原指标聚合；page CTE 排序/裁剪；最终一次返回总数及 JSON 行数组。空页同样返回总数，不用额外 count 查询。

所有指标表达式、舍入、有效样本条件不变；特别保留：

```sql
AVG(CASE WHEN duration_ms > 0 AND output_tokens > 0
         THEN output_tokens * 1000.0 / duration_ms END)
```

没有替换成 SUM(tokens)/SUM(duration)，没有改变平台归属或时间过滤，也未新增索引。物化的是模型分组小结果，非完整明细。

### 共享缓存与资源边界

- handler 用 UTC 分钟向下取整作为 end，start=end-原时长；返回现有 start_time/end_time 即真实截至时间。
- key 包含版本、全局管理员权限范围、UTC 起止时间、平台规范化值、group_id、time_range、Top N、page、page_size。timezone 目前不影响计算，所以不在 key；将来若支持自然日/时区维度，必须同步加到 key。
- 当前路由经 AdminAuth，所有管理员读取相同全局数据；未来若增加细粒度权限，必须变更 scope/key 版本，不能复用此缓存。
- Redis 成功结果 TTL 120 秒，不缓存错误；分钟时间桶避免每次 now 不同导致 key 变化。**TTL 不等于允许返回任意 120 秒旧窗口**：新分钟会产生新窗口/key，因此同条件正常最多每分钟计算一次；120 秒用于短期保留旧窗口的在途复用。
- 正常新鲜度：请求时窗口截止最多落后 60 秒，加上计算/等待最多 58 秒，接收时约不超过 118 秒（不含异常传输时间）；UI 使用返回 end_time，而非伪装为浏览器当前时间。历史数据修正同样可在下一分钟重新计算。
- 进程内 singleflight 合并同 key；Redis 全局计算锁限制**所有该端点条件合计最多一个明细计算**，避免不同页面/筛选并发击穿。等待者每 200ms 查缓存/尝试锁，最多 58 秒，可独立取消。
- 锁 token 采用随机值，SET NX 租约 65 秒，Lua compare-and-delete 异常释放，1 秒独立清理上下文。持锁后再次查缓存，关闭 GET/加锁竞态；崩溃由租约恢复。
- repository 查询 context 最长 55 秒，整个计算/等待 58 秒，HTTP 客户端 65 秒；取消传递到 QueryRowContext/PostgreSQL。不同条件抢锁可能超时，并非无限排队，界面可手动重试。
- Redis 故障时返回可重试 503，避免直接查库形成风暴。未配置 Redis 的独立 service/test 保留进程内合并路径；正常生产 provider 已注入 Redis，源码/生成 Wire 同步。
- 首个同 key 请求拥有计算上下文，它取消时该 flight 的其他等待者也会收到错误，后续可重试；独立等待者取消不会取消其他请求。此取舍避免所有用户离开后仍继续高成本计算。
- **跨实例保证依赖共享 Redis 实例、DB 和命名空间**。若两节点分别使用本地 Redis，本次只能限制各自实例，不能保证数据库总并发 1；上线前必须核实。Redis 主从切换/锁键被驱逐可能出现短暂重复计算，锁不是强一致数据库事务锁。数据库 timeout 仍为最终资源边界，不能据此宣称任意网络故障下严格零重复。

## 4. 受控 PostgreSQL 执行计划与结果

环境：本机独立 PostgreSQL 17、20 万合成行，100 个模型，约 1KB/行填充；created_at 有索引并执行 ANALYZE，30/31 天命中约 96.8%，非生产环境。为稳定对比关闭并行计划。原计数、新旧统计在同一时间边界执行 EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)，允许在该隔离库实测。

[完整计划](Token请求统计本地执行计划-2026-11-04.txt)。首次顺序观测如下，不代表冷缓存或生产结果：

| 指标 | 原 count + result | 新单 SQL |
| --- | ---: | ---: |
| 明细 Seq Scan 次数 | 2 | 1 |
| 明细匹配行/次 | 193549 | 193549 |
| 根节点 shared hit+read 块合计 | 57150 | 28572 |
| shared read 块合计 | 24749 | 12342 |
| 执行时间合计 | 54.913 + 83.083 = 137.996 ms | 83.842 ms |
| Top 20 全字段结果 | 基准 | JSON 全字段相等 |

shared read 是 PostgreSQL buffer miss，不等于操作系统实际物理盘读取；不能以此宣称生产磁盘 IO 已减半。高比例范围本地选择顺序扫描是合理候选，即使存在 created_at 索引，不能直接归因为缺索引。缓存/页面大小/磁盘和数据分布不同，生产需要其自己的计划和采样。

## 5. 长期预汇总方案（仅设计，未实现）

收益：将大量历史明细 IO 改为少量模型/小时桶读取；成本：新增表、后台任务、回填和修正链路，可能增加写放大、存储、运维与一致性成本。先验证单扫描、60 秒节奏、共享缓存后的生产效果；若冷查询仍超出可接受时延或一分钟一个重查询仍占满磁盘，再独立实施，不在本次引入大迁移。

建议 UTC 小时桶，保存 model、group_id、account_id 等保持现有过滤必需的维度，另存 request_count、output_tokens_sum、duration_sum/duration_nonnull_count、first_token_sum/first_token_nonnull_count、tps_ratio_sum/tps_valid_count。TPS 分子必须累加每条有效请求 `output_tokens * 1000.0 / duration_ms` 的 numeric 结果，再除有效样本数，最终按原逻辑舍入，禁止直接平均桶均值或总 token/总时长。first_token 非空计数包括零值；duration 非空均值包括零/负值，不能误用 TPS 有效条件；全 NULL 的各指标继续按原 NULL/COALESCE 返回。

- 查询完整历史 UTC 小时桶；最前和最后未对齐小时的片段使用明细，两类用严格不重叠 `[start,end)` 边界合并原始分子/样本数，最后统一舍入。不能把边界整桶全计入，也不能遗漏滚动 30d 最前部分小时。
- 时区仅影响将来有明确需求的展示/自然日边界。现有滚动小时/天时长保持不变，DST 日不擅自变更为 24 小时以外口径。
- 现有平台归属使用**当前** groups/accounts：若汇总直接固化 platform，组/账号平台变化、删除会改变历史归属语义。需要保留 group/account 维度并查询当前归属，或由业务明确接受快照语义；这会增加桶基数与连接成本，必须先测算。
- 迟到记录、UPDATE、DELETE、清理任务都需写入可重放的“受影响小时桶”队列/事务 outbox；简单 created_at 水位无法捕捉迟到/删除，不能作为完整方案。
- 对脏桶从事实表重算并原子替换，幂等唯一键；桶数据和检查点同一事务提交。回填可分小时、节流、失败续跑，重跑不重复累加；生产回填单独审批和容量计划。
- 多实例任务使用 DB/共享锁、租约及 fencing/事务检查点，不能仅靠进程锁。队列消费、崩溃恢复、清理与增量并行需要明确顺序；已删除事实无法凭空还原，必须保留修正证据或重算桶。
- 验证 TPS numeric 累加精度/最终舍入与原 SQL、NULL/零值、时区边界、迟到、删除修正、回填重入、桶交界及跨节点抢占后再开放。

## 2026-11-04 后续决策：数据库共享缓存

用户确认多应用共享 PostgreSQL，但 Redis 不保证共享，并授权数据库缓存＋互斥实现。当前代码已用 PostgreSQL 缓存表与事务 advisory lock 替代本文第 3 节 Redis 实现；本文首轮测试和无迁移结论仅描述该阶段，不再作为当前交付方案。生产只读核验由用户要求暂时跳过。最新行为、迁移 249、测试及回滚见 [数据库缓存实现记录](Token请求统计数据库缓存实现-2026-11-04.md)。
