## 目标与流程

以 0.2.22-hcai 的实际流程为基线，2026-11-18 按用户要求把两级 PR 的手动点击合并改成 GitHub auto-merge：固定上游正式 Release 标签和提交 → 从 dev 双亲合并生成候选 → 本地验证 → PR 到 dev → 最终 CI 失败时 AI 修复并重跑 → CODEOWNER 审核及必需 CI 通过后自动合入 dev → 自动创建 dev 到 main PR → 独立 CI 与 CODEOWNER 审核通过后自动合入 main → main 现有工作流发行 → 下载正式附件核验 → 两级纯 Markdown PR 补录发行证据并按相同门槛自动合并 → 检查 dev/main 内容一致并清理本次临时分支。生产部署仍独立安排。

候选生成由 `.github/workflows/upstream-sync.yml` 负责；失败 CI 的有限次数修复由 `upstream-ci-repair.yml` 负责；`upstream-pr-merged.yml` 在 PR 合并后创建下一层 PR 或核对收尾；维护者仅在正式 Release 完成后手动触发 `upstream-publish.yml` 核验产物并创建证据 PR。新 PR 创建时通过 `enable-auto-merge.sh` 预设 merge commit 合并，只有 GitHub 分支规则实际满足时才执行。确定性 Git、SHA、PR 和产物校验在 `.github/upstream-sync/`；Codex 指令在 `.github/codex/`。现有 `ci.yml` 与 `amd-linux-release.yml` 保持发行权威。

本地开发的独立入口：维护者在本地 `dev` 提交并推送后，`dev-to-main.yml` 检查本次 SHA 与 `main` 的内容差异，AI 只生成包含更新范围、功能影响、HCAI 定制影响及验证风险的 PR 说明。工作流创建或更新 `dev → main` PR，并预设 auto-merge；最终 CI 与 CODEOWNER 审核满足后自动合入 `main`，仍由现有工作流判断是否发行。若推送对应上游候选或发行证据 PR，则交由既有 `upstream-pr-merged.yml` 接续，避免重复开 PR。已有其他类型的 `dev → main` PR 时停止，交人工核对；新 `dev` 推送使旧运行过期时由新运行处理。AI 不修改代码或文档，版本及文档同步仍由本地开发任务在推送前完成。生产部署独立安排。
