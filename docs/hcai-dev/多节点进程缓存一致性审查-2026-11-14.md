# 多节点进程缓存一致性审查

2026-11-14。基线：0.2.21-hcai 本地工作树及尚未提交的系统设置 HTML 失效修复。仅源码审查、更新文档；不修改业务代码、不连接生产、不部署、不远程写入。检查设置运行时、WebSearch、渠道、错误透传、TLS 模板、插件及认证/订阅失效入口。非全项目每个缓存的形式化完整证明，没有生产重现实验。

## 结论和优先级

仍有同类风险，前一轮修复仅覆盖 HTML/CSP origins，不能称作所有设置跨节点同步已经完成。

### P1：客户端 IP 信任设置只更新当前进程

证据：setting_update.go refreshCachedSettings 调用 cfg.SetForwardedClientIPSettings；setting_service.go 启动加载一次数据库配置；config.go:885 存入本地 atomic.Pointer。server/middleware/session_binding.go:20 每请求读此指针。未找到 TTL、后台读库或跨节点更新该指针的路径。当前新增通知消费者仅运行 router 的 HTML/origins 回调，不更新 cfg。

触发：节点 A 修改 api_key_acl_trust_forwarded_ip / forwarded_client_ip_headers，节点 B 保留启动时的信任策略和头列表。影响：请求客户端 IP/会话绑定及相关 IP ACL 判断可能跨节点不同；关闭信任后其他节点仍沿用旧信任策略，属于安全配置传播问题，不代表已经发生攻击。

建议：收到设置事件后从 DB 加载这组运行时配置并原子更新；独立于本地保存回调，不再次发布。覆盖关闭信任、头列表替换、读库失败、恢复与双节点隔离测试，不在网络故障时回退为更宽松信任。

### P1：WebSearch Manager 长期保持旧实例

证据：websearch_config.go:166 附近独立 Set 写配置；仅本机更新 webSearchEmulationCache 并在178重建 Manager。rebuildWebSearchManager 调用者只有保存和 SetWebSearchManagerBuilder 启动初始化。gateway_websearch_emulation.go:39 全局 atomic.Pointer 存 Manager，热路径先检查该指针；普通配置虽有 TTL，TTL 到期只更新配置，不重建 Manager。

触发：A 开启/修改搜索供应商、API Key、代理等，B 不会对应重建 Manager；B 启动时 Manager 为 nil 时，即使之后 DB 开启，入口先判断 nil 可一直跳过搜索模拟。旧 Manager 非 nil 时可能继续使用旧供应商/凭据/代理。关闭总开关时设置 TTL 会影响入口，不应笼统说关闭一定永久无效。

此独立写入口也不经过 onUpdate，因此仅扩展通用事件消费者还不够，须在该独立写入成功后发布事件，并让各节点安全重建 Manager。消息仍不可携带 Key。代理本身变更是否触发 Manager 重建也应加入专项回归。

### P2：错误透传规则、TLS 指纹模板丢通知后缺少恢复兜底

证据：两者 service 构造时加载本地快照并以 context.Background 订阅；CRUD 已有 invalidateAndNotify，所以正常 Redis 广播下不是完全不通知的问题。但 error_passthrough_service.go:181 非 nil 本地规则直接返回；tls_fingerprint_profile_service.go:137 热路径直接读 map。repository 对应缓存 Get 也先返回本地无 TTL 快照。Redis 中的24h TTL不能使这些本地快照到期。

触发：B 订阅断开期间 A 更新，或发布失败/接收后重载失败；即使连接恢复，Pub/Sub 不重放旧通知，订阅没有重连后读库校准，也没有周期本地快照过期。B 可长期保留旧规则/模板，直至新通知等触发重载。两套订阅 context.Background 未由 service Stop 取消，建议同时规范其生命周期；不能仅以 Redis 客户端最终关闭代替明确的退出管理。

建议：复用现有 channel，增加重连校准、定期版本/TTL兜底和受控关闭；接收只清理/重载不重发。特别验证通知重载失败后自动恢复。不要新建客户端或新增公开清缓存接口。

## 有延迟但不是同样长期不刷新

| 范围 | 源码行为 | 判断 |
| --- | --- | --- |
| 渠道定价/映射 | ChannelService 发布并订阅，收到仅 clearCache；缓存 loadedAt TTL 10分钟 | 正常即时广播；丢消息后仍有10分钟过期兜底，期间可能节点不一致，非永久旧值 |
| 网关转发开关、后端模式、客户端版本上下限、调度阈值、Codex策略等 | setting_gateway_runtime.go 大多60秒TTL、错误短TTL | 本机保存立即刷新，其他节点健康读库情况下等TTL；现HTML事件未清理这些缓存 |
| 面板限流设置 | setting_panel_rate_limit.go 60秒TTL，独立保存只更新本地 | 健康DB下短暂不一致，故障时保留旧值并重试 |
| OpenAI API Key 健康熔断设置 | setting_openai_apikey_health.go 30秒TTL | 有过期读取，不等同无限旧快照 |
| 插件运行绑定 | PluginManager reconcileLoop 定期以DB为权威协调 | 已有周期校准，不应按同类无失效路径误报；未证明插件全部功能端到端一致 |
| API Key/订阅缓存 | 已有专用发布订阅与认证跨区失效机制 | 未发现与HTML完全相同的“只有本机回调”缺口；不代表完成全部故障模式审计 |

以上TTL是正常读库条件下的缓存策略，不是数据库不可用时的最大陈旧时间保证。另渠道 buildCache 无代次写回保护，和HTML类似的并发旧构建覆盖失效存在结构性风险，但有TTL兜底；未做受控竞态复现，不列为已重现故障。

## 下一步建议

先补IP信任配置同步与WebSearch独立写入口/Manager重建，再修错误透传及TLS缓存重连校准。沿用当前设置事件元数据协议，按变更域刷新，避免所有事件都重建有状态Manager；增加双节点不同config实例测试。不能直接从远端调用 refreshCachedSettings：它会调用 onUpdate 并造成发布回环，而且携带的默认/未读取字段可能覆盖运行时值。

本轮没有增加测试或重跑测试：没有业务改动，结论来自上述源码读写/失效路径；前一任务测试通过不冒充这四项已修复。需要后续单独实现与故障回归。
