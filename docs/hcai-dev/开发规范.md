# HCAI 开发规范

适用范围：本仓库所有 HCAI 新功能、修复、文档、测试及工程改动。依据当前开发实践制定；“必须”是流程要求，不代表远程规则已自动启用。

## 1. 分支与权限

正常流程为功能分支 → dev → main，每个边界通过 PR。按现有 CONTRIBUTING.md 使用 feat/、fix/、docs/、chore/ 分支。main 不直接推送；dev 紧急 CI 修复仅按维护者授权例外执行。禁止强推或删除共享分支。

检查请求只允许审查；修复、推送、合并、发布和生产部署是不同动作。用户要求创建 PR 不等于允许合并，创建 Release 不等于允许上线。跨区域部署只操作发布单中的节点。

开始前检查 git status、当前分支、远程地址、基线提交及已有修改。保留他人改动，不使用 reset --hard 或 checkout -- 清理工作区。不要直接提交所有暂存文件。

## 2. 实现与兼容

1. 先读代码和测试，再确认行为边界；按功能最小范围修改，不夹带无关重构。
2. 使用现有 Vue、Go service/repository、配置和错误处理模式。
3. 设置必须覆盖默认值、DTO、更新、存储、读取、公开设置、前端类型、路由/菜单及测试；插件开关曾因遗漏写入无法开启。
4. 区分展示价、官方参考价和实际扣费链路；展示修复不得顺带改扣费。
5. 中文和英文 locale 同步修改；页面不能直接显示翻译 key。静态首页中文内容需单独维护。
6. 异步加载有明确 loading、成功、失败/回退状态；不能让旧首页在正常加载阶段闪现。
7. 不向跨域菜单附加用户 Token、ID 或当前页面 URL。对 URL、日志、webhook 和 OAuth 回调做安全校验。
8. 多节点后台作业必须声明锁、幂等、租约、失败策略与清理行为，不能假设进程内锁等于集群互斥。
9. 数据库变更新增迁移，不改已发布迁移；评估锁表、默认值、回填、索引及旧程序兼容。不可逆迁移必须明确写明。
10. 修改依赖或构造函数后检查所有调用者、测试桩、Wire 源码/生成结果；生成文件与源定义一起维护。

## 3. 验证门槛

前端在仓库根目录执行：

```bash
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend run lint:check
pnpm --dir frontend run typecheck
pnpm --dir frontend run test:run
pnpm --dir frontend run build
```

后端在 backend 目录执行：

```bash
go test -tags=unit ./...
go test ./...
CGO_ENABLED=0 go build ./cmd/server
```

以上与当前 PR CI 对齐。额外执行 git diff --check。源码发行验证必须先构建前端，再执行带 -tags embed 的 Go 构建。根目录 make test 包含 golangci-lint 和前端关键测试子集，不等同完整前端测试。

测试规模随风险增加：窄改动增加定向回归；计费、支付、认证、迁移、多节点增加集成与失败路径验证。UI 改动覆盖桌面/移动端、深浅主题和异常状态。涉及支付使用沙箱；禁止未经许可消耗真实上游额度。

超时、手动终止、依赖不可达必须记录为“未完成”，不能写成通过。CI 失败先读日志和定位提交，不因“看起来只改了前端”直接跳过后端检查。

## 4. PR 与交付

PR 写清需求、影响范围、验证命令和结果、迁移/配置、风险、回退方案；只有文档变更时明确说明。提交前逐文件检查暂存区，排除凭据、运行数据和构建产物。docs/* 默认被忽略，确需跟踪时对具体文档使用 git add -f，不整体放开所有文档。

Backend checks、Frontend checks 必须成功，讨论解决并按仓库政策获得 CODEOWNER 审查。远程是否已配置保护规则需另行核实。更新自定义清单和相关功能说明；交付列出未验证项，不把代码存在当作线上验收。

## 5. 文档同步更新规则（必须）

开发、修复、重构、上游合并、代码审查、CI 排障、版本发布和部署过程中，必须同步维护 `docs/hcai-dev/` 下对应文档。文档属于交付内容，不得以“代码完成，文档以后补”为由跳过。

### 更新范围

| 变更或活动 | 必须检查并按实际影响更新 |
| --- | --- |
| 功能新增、修复、删除或行为变化 | HCAI自定义功能清单.md：行为、入口、配置、数据、测试、上游边界和已知限制 |
| 定制归属、上游基线或文件范围改变 | HCAI全量差异与提交附录.md：明确新基线、完整范围与历史关系 |
| 开发工具、测试、CI 或贡献流程调整 | 开发规范.md；涉及发布时同时更新版本发布规范.md |
| 上游更新和冲突处理 | 上游更新合并规范.md 中受影响的规则、对应版本合并记录、自定义清单及差异附录 |
| 提交格式、类型或历史修正策略调整 | HCAI提交消息规范.md |
| 版本编号、标签、构建、附件或发布门槛变化 | 版本发布规范.md 及对应版本发布记录 |
| 环境、区域、节点职责、迁移或回退变化 | 部署与多区域运维规范.md 及对应部署记录 |
| 审查、诊断或验证发现文档与实现不符 | 更正受影响文档；记录证据、风险、状态和未验证项，不把建议写成已实现 |

不要求每次改动机械修改所有文档。执行一次发布/部署只追加对应记录，不为凑变更改写稳定规范；确实没有文档影响时，必须在 PR 或交付说明中写出检查范围及无需更新的具体理由，由审查者确认。

### 更新时机与记录

1. 开始前阅读相关规范与清单，明确本次受影响文档。
2. 实现、合并或审查结论变化时同步更新，不等到发布后补记。业务变更及说明应进入同一 PR；CI 或部署后才产生的证据在该阶段完成后及时追加，不提前写成功。
3. 记录适用版本/基线 SHA、日期、变更原因、当前行为、验证命令和结果、已知风险。对未修复、未执行、失败和已验证状态分别标明。
4. 历史快照保留原基线；新版本新增章节或带基线的新记录，必要时重新生成附录，不在旧快照下混入新数据。历史失败及冲突处理不删除。
5. 新记录放在 `docs/hcai-dev/` 并使用中文名称，例如 `上游合并记录-0.2.8-hcai.md`、`审查记录-0.2.7-hcai.md`、`部署记录-版本-日期.md`。已有历史文档可保留位置并链接引用，不重复维护两份相同事实。
6. 交付前检查相对链接、文件名、代码块、版本信息和 `git diff --check`；明确列出更新文档和未完成事项。

只读审查可以记录文档发现，但不因此获得修改业务代码、推送、发布或部署权限；用户明确禁止文件修改时，应报告待同步文档和建议修改内容，不落盘。禁止把生产凭据、个人数据或敏感日志写入文档。

### 审查门槛

审查者必须核对代码与文档是否一致，以及自定义行为是否遗漏。缺少必要文档更新、用过期验证冒充当前结果、把未实现功能写成已实现，均阻断交付完成和合并放行。该规则通过人工审查与 PR 清单执行，当前 CI 尚未自动验证语义上的文档同步。
