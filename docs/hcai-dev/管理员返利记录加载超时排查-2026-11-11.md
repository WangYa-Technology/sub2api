## 主要发现：P1 查询退化风险，隔离环境已复现

位置：`backend/internal/repository/affiliate_repo.go:633` 起。

返利查询先执行总数查询，再执行分页 SELECT，两个阶段共享多表关联。其中兑换码关联：

```sql
LEFT JOIN redeem_codes rc ON ual.source_type = 'redeem_code'
  AND ual.source_ref IS NOT NULL
  AND (ual.source_ref = rc.id::text OR ual.source_ref = rc.code)
```

`id::text` 无法直接使用普通 bigint 主键索引完成等值查找，和 code 的 OR 混合后可产生嵌套循环及兑换码全量扫描。无搜索条件的总数仍保留该关联，COUNT 不受分页20条的限制，第一页也可能等待所有流水与兑换码匹配。现有 source_type/source_ref 索引位于流水表，不能直接解决兑换码侧此匹配。实际执行计划取决于数据、索引和统计信息，不能把合成耗时直接等同生产耗时。

另有潜在正确性问题：同一 source_ref 若同时等于一个兑换码 ID 的文本和另一个兑换码 code，可匹配两行，造成计数与列表重复；尚未确认生产存在此类数据。

### 隔离复现

本机 PostgreSQL 17，临时端口55439，合成100个用户、100000个兑换码、2000条 accrue 流水，设置主键、code 唯一索引和相关流水索引，ANALYZE 后执行从源码抽取的原始 COUNT 关联。未使用生产数据。

- 原 COUNT 执行计划：Nested Loop Left Join；redeem_codes Seq Scan + Materialize。
- 原 COUNT 在 statement_timeout=8s 下被取消。
- 将外层限制为100条时，执行约1297.656ms，Join Filter 丢弃9999900个候选组合。
- 无搜索场景，去掉不必要外关联、保留 users inviter 存在性约束后的对照 COUNT：全部2000条约0.357ms。此为定位用对照 SQL，不是已实现修复；存在搜索时不能直接删掉其依赖关联。
- 既有前端测试：`pnpm exec vitest run src/views/admin/affiliates/__tests__/AdminAffiliateRecordsTable.spec.ts`，3/3通过。其 API 被 mock，不覆盖真实SQL性能。
- 临时证据：`/tmp/hcai-affiliate-review-20261111/` 下 probe.py、probe.sql、result.txt、small-plan.txt；仅本机临时文件，可能被清理。

## 建议修复方案（未实施）

1. 无搜索 COUNT 只保留流水过滤及必要的用户存在性约束；有搜索时用明确的 EXISTS/可索引关联，避免扩大结果集。
2. 兑换码引用优先按明确的 ID 语义关联；当前 AccrueInviteRebateForRedeem 写入 redeemCodeID。若需兼容历史按 code 存储，先确认历史数据语义，再采用确定优先级的索引查询和回退，保证每条流水最多匹配一个兑换码。不得直接删除历史兼容或未经保护将任意文本 cast bigint。
3. 无关联搜索/排序时先筛选分页流水，再补充展示字段；搜索及关联列排序必须保持全局语义。补稳定唯一键排序，避免同时间戳翻页漂移。
4. 加入真实 PostgreSQL 回归及执行计划验证，覆盖订单/兑换码/管理员充值、空来源、已删除来源、ID/code冲突、筛选与排序；避免仅靠mock测试。
5. 不把前端30秒超时调大当作根本修复。不为此修改返利计算、余额和账本写入。
