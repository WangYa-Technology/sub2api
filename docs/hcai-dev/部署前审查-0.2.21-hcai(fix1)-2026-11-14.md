## 4. 审查发现与行为边界

### 4.1 P2：既有测试桩数据竞争，待修复

- 位置：[usage_cleanup_service_test.go](../../backend/internal/service/usage_cleanup_service_test.go) 第58–68、583、611行。
- `dashboardRepoStub.recomputeCalls` 是普通 int，异步 `RecomputeRange` 执行 `++`，两个测试在 `require.Eventually` 中无同步地读取。race 实际报告读写均指向该测试变量。
- 失败用例：`TestUsageCleanupServiceExecuteTaskDashboardRecomputeError`、`TestUsageCleanupServiceExecuteTaskDashboardRecomputeSuccess`。
- 原 `.21`、本修订及上游基线中的该测试文件 blob 均为 `17f21bef36957d7a9ebf89c9e4042cb60e6cbf08`。fix1 未修改该文件或 `dashboard_aggregation_service.go`。
- 影响：扩大 race 验证范围时会失败，降低测试可靠性；不能据此声称生产用量清理发生相同数据竞争，也不能声称整个 service race 已通过。建议后续使用 atomic/mutex 保护测试计数器并回归。本次审查未修改测试或业务代码。

### 4.2 Redis 故障时保存仍成功，但延迟不严格限定为1秒

[setting_invalidation.go](../../backend/internal/service/setting_invalidation.go) 第74–92行先同步执行本地失效/刷新，再调用 Publish；发布错误只告警，不作为保存错误返回，HTTP回归也验证了这一点。

发布使用1秒context，但[redis.go](../../backend/internal/repository/redis.go) 第33–44行复用的客户端未启用 `ContextTimeoutEnabled`。当前 go-redis v9.22.0 会在部分网络读写路径使用自身超时；默认配置建连5秒、读写各3秒，并有客户端默认重试。因此不能承诺网络黑洞等故障下保存必在1秒内返回，前置本地数据库刷新及锁等待也计入耗时。此限制在原修复文档已有披露，本轮确认实现一致。后续可单独优化保存尾延迟，不能为此新建另一套Redis客户端或无审查地改变全局超时策略。

### 4.3 失败时不同运行时采用不同策略

| 范围 | 当前行为及影响 |
| --- | --- |
| HTML/CSP | 清除HTML缓存；frame origins读库失败保留原列表并告警，数据库恢复后的通知/周期刷新再更新。不能宣称读库失败时已应用新CSP |
| 转发IP信任 | 运行时读库或头格式错误会禁用兼容转发信任，恢复后重新读取；此期间客户端IP按现有 trusted_proxies/直连回退，可能影响IP白名单、会话绑定或限流的可用性，不是扩大信任 |
| WebSearch | 配置读库失败清空Manager，后续重建；已配置代理但解析失败的供应商被跳过，不静默直连。可能临时无法搜索 |
| 错误透传/TLS模板 | 周期读库失败保留已有运行快照并告警，后续重试；不宣称失败时已同步新规则 |

依据：`setting_invalidation.go:157`、`websearch_config.go:237`、`server/http.go:56`、`error_passthrough_service.go:217`、`tls_fingerprint_profile_service.go:207`。这些是当前安全/可用性取舍，未发现将读失败误判为已同步的实现。

### 4.4 一致性与关闭时限

- Pub/Sub不持久化；30秒是补偿调度周期，数据库/网络故障时不是一致性SLA。接收重复/乱序消息重新读库，结果幂等，但不意味着同一事件只触发一次读取。
- 新增低频直读：每节点对设置/CSP/IP/WebSearch、规则和模板周期校准。三个节点增加数据库读取，尚未进行生产容量测量。
- HTML渲染使用generation检查，失效前已开始的旧渲染不能重新填入长期缓存；该在途响应仍可能返回一次旧快照。已经打开的SPA没有新增浏览器推送，需要刷新页面。
- 订阅Stop取消并关闭连接，等待工作协程结束，再关闭共享Redis/数据库。设置刷新使用独立Background超时，正在执行的读取不会因Stop立即取消；`wire.go:145`的三个Stop发生在原10秒cleanup上下文创建之前。因此10秒不是整个退出过程的硬上限，应核对实际systemd停止超时，不承诺即时退出。本轮不可达Redis取消测试通过。
- 新channel为Redis实例级，**不同Redis DB编号不隔离Pub/Sub**。共享实例的其他环境若共用channel，可能收到额外刷新；消息不会携带或应用其他环境配置，但会增加读库。当前用户提供的是同一业务三节点共享库/Redis的适用拓扑。

## 5. 多节点修复与 HCAI 保留情况

逐项复核实现：

1. `SettingService`保存成功后触发既有回调，先清本机HTML并刷新frame origins，再发布。部分更新已落库但后续整份设置读取失败时仍会通知；写库失败不通知。
2. channel **`sub2api:settings:updated:v1`**，消息仅含 `type/node/version/time`，type为`settings.updated`或`websearch.updated`；node与version为进程/事件UUID，time为Unix毫秒。没有完整设置、密钥、代理URL或用户数据。
3. 所有升级节点接收后执行本机HTML/CSP刷新及只读IP/WebSearch校准；自发消息跳过，接收不调用保存、不重发；畸形/超长消息忽略。没有新增公开清缓存接口。
4. 错误透传、TLS模板继续使用 `error_passthrough_rules_updated`、`tls_fingerprint_profiles_updated` 及`refresh`消息；收到通知、重连确认或30秒补偿时直接查数据库，绕过陈旧L1/L2。停止资源纳入Wire源码和生成结果。
5. 使用同一个已注入Redis客户端。nil Redis保留原有本地更新；Redis离线时本地失效不依赖发布成功。整个系统其他功能对Redis的依赖未因此取消。
6. 对原 `.21` 比较，fix1没有更改前端源码、locale、首页静态资源、模型广场/渠道价/实际扣费、返利查询实现、支付或多区域任务协调代码；原返利加载修复保留。模型广场仍设置`PreferChannelPricing=true`，首页仍有HCAI加载/成功/回退状态。插件版本只对精确`X.Y.Z-hcai(fixN)`规范化比较，协议及tested声明限制保留。

本轮未发现HCAI自定义被整块覆盖的证据。上述是差异和定向测试结论，不表示所有自定义功能均完成了生产端到端验收。更新检查仍按数字基础版本比较，`.21-hcai`到fix1不保证出现自动更新提示，应以正式Release/SHA人工识别。
